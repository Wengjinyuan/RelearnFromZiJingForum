# REBUILTZIJINGFORUM：简历技术亮点与面试追问地图

> 目标不是把技术名堆进简历，而是让每一项都形成“业务问题 → 项目方案 → 代码证据 → 缺陷边界 → 延伸追问”的闭环。只写你能沿着这条链讲下去的内容。

## 1. 先给技术能力分级

| 等级 | 含义 | 简历应该怎样写 |
| --- | --- | --- |
| A：默认主链已实现并自动测试 | 不依赖外部中间件，H2/MySQL 路径有测试证据 | 可以写“实现、设计、通过测试验证” |
| B：代码已实现，但外部服务未真实联调 | Redis、RabbitMQ、Elasticsearch、浏览器 SSE 等已有代码和开关，缺少真实服务故障验证 | 写“设计并提供可选实现”，不要写“生产落地、解决高并发” |
| C：文档中的演进方案 | 代码尚未实现，例如 Bloom Filter、混合 Feed、MFA、完整 refresh token | 面试可说“下一步会这样做”，不能写成项目成果 |

当前可以确认的自动化验证是默认 H2/MySQL 主链。Redis、RabbitMQ、Elasticsearch 与浏览器 SSE 的真实集成边界必须主动说明，这种诚实不会减分，反而能证明你懂“依赖存在”和“生产验证”的区别。

## 2. 最值得写在简历上的技术

### 2.1 Spring Boot + Spring MVC 分层与纵向功能包

**业务问题：** F01-F11 功能多，如果 Controller、Service、Mapper 横向堆在一起，学习、权限检查和修改边界都会混乱。

**项目做法：** 按 account、profile、post、comment、interaction、follow、notification、search、home、message、admin 组织纵向功能包；请求经过 DTO、Controller、Service、Mapper、数据库，再输出 VO/ApiResponse。

**技术具体解决：**

- Spring MVC 负责 HTTP 路由、参数绑定和拦截器链。
- Bean Validation 负责输入形状和基础约束。
- Service 负责事务、权限和业务不变量。
- Mapper 负责明确的数据读写。
- GlobalExceptionHandler 统一 400/401/403/404/409/500 响应。

**简历安全写法：**

> 基于 Spring Boot 3 按业务能力拆分 F01-F11 纵向模块，建立 Controller-Service-Mapper 调用链、DTO/VO 边界、Bean Validation 与统一异常响应，降低跨模块权限规则遗漏。

**面试追问地图：**

1. 为什么不按 controller/service/mapper 三个大包组织？
2. Controller、Service、Mapper 各放什么，事务为什么通常放 Service？
3. Filter、Interceptor、AOP、Spring Security Filter Chain 有什么区别？
4. Bean Validation 为什么不能替代业务校验和数据库约束？
5. 全局异常处理怎样避免把内部异常信息泄露给前端？

**事实等级：A。**

### 2.2 MySQL 关系建模、事务、唯一约束与条件更新

**业务问题：** 重复注册、重复点赞、重复关注、双人重复会话、消息重试、并发审核都会产生竞态；仅靠 Java “先查再写”不可靠。

**项目做法：**

- account/email/mobile 使用 UNIQUE。
- like_record、favorite、follow_relation 使用组合唯一约束。
- conversation 使用排序 pair_key + UNIQUE。
- private_message 使用 sender_id + client_message_id 去重。
- 管理状态用 id + oldStatus 条件 UPDATE 检测竞争。
- 关系变化、冗余计数、审计记录在同一事务提交。

**简历安全写法：**

> 使用 MySQL 唯一约束、幂等接口、Spring 事务、原子计数与条件更新处理注册、互动、关注、私信和审核中的并发竞态，避免仅依赖“先查再写”，并通过影响行数识别乐观并发冲突。

**面试追问地图：**

1. 为什么“先查再插”会有竞态？UNIQUE 冲突怎样转换为幂等成功或 409？
2. ACID 分别是什么？`@Transactional` 为什么管不了 Redis、MQ、ES 和文件？
3. READ_COMMITTED、REPEATABLE_READ、SERIALIZABLE 有什么差异？
4. 乐观锁和悲观锁怎样选择？条件更新影响 0 行代表什么？
5. 死锁怎样出现，数据库怎样检测，应用为什么要有限重试？
6. 冗余计数为什么会漂移，怎样设计离线对账？

**事实等级：A。**

### 2.3 MyBatis-Plus + JdbcTemplate：CRUD 与复杂 SQL 分工

**业务问题：** 单表 CRUD 需要减少样板代码，Feed、统计、批量查询等 SQL 又需要看得见、可控制。

**项目做法：** F01-F03 等实体 CRUD 使用 MyBatis-Plus；F04-F11 大量查询通过 JdbcTemplate/Mapper 写明确 SQL，包括批量作者查询、关注流 JOIN、首页聚合和游标消息。

**简历安全写法：**

> 结合 MyBatis-Plus 与 JdbcTemplate：用前者简化单表 CRUD，用后者实现可审查的 JOIN、聚合、条件更新和游标查询，并通过批量查询避免评论列表 N+1。

**面试追问地图：**

1. MyBatis、MyBatis-Plus、JPA/JDBC 各有什么取舍？
2. 什么是 N+1，怎样通过 SQL 日志/APM 发现？
3. IN 批量查询、JOIN、缓存各适合什么场景？
4. SQL 参数绑定与动态表名/字段名有什么注入差异？
5. OFFSET 为什么越翻越慢，keyset pagination 需要什么索引？

**事实等级：A。**

### 2.4 BCrypt + JWT + tokenVersion 可撤销鉴权

**业务问题：** 密码不能明文保存，后续请求需要可信身份，改密/封禁/角色变化后旧 JWT 又必须失效。

**项目做法：** BCrypt cost 10 保存密码哈希；JWT 写入 sub、role、ver、iat、exp；AuthenticationInterceptor 验签后查询数据库，比较 status 与 token_version，再生成 CurrentUserDTO。

**简历安全写法：**

> 实现 BCrypt 密码哈希与 JWT 鉴权，通过 AuthenticationInterceptor 构造可信当前用户，并引入 tokenVersion 在改密、封禁等安全状态变化后撤销旧令牌，避免完全无状态 JWT 无法即时失效。

**面试追问地图：**

1. 哈希和加密有什么区别？BCrypt 为什么比 MD5/SHA 更适合密码？
2. BCrypt 的 salt 在哪里，cost 怎样压测和渐进升级？
3. JWT 是签名还是加密？payload 能不能放密码和隐私？
4. JWT 与 Session 怎样选？各自如何撤销、扩容和防攻击？
5. access token/refresh token 为什么要分开，rotation 与 reuse detection 是什么？
6. token 放 LocalStorage 与 HttpOnly Cookie 各有什么 XSS/CSRF 风险？

**事实等级：A；refresh token、MFA、登录限流属于 C。**

### 2.5 幂等设计：HTTP 语义、业务键与数据库约束

**业务问题：** 用户双击、客户端超时重试、MQ 重投可能重复点赞、重复关注、重复消息和重复通知。

**项目做法：**

- 点赞/关注使用 PUT 与 DELETE 表达目标状态，不使用 toggle。
- 私信由客户端为一次发送生成稳定 clientMessageId。
- 通知由 event_key 标识同一业务事件。
- UNIQUE 是最终不变量，只有首次真实写入才触发计数、未读和通知副作用。

**简历安全写法：**

> 为互动、关注、私信与通知设计端到端幂等：使用 PUT/DELETE 目标状态、clientMessageId/event_key 业务键和数据库 UNIQUE，确保网络重试与消息重放不重复增加计数或未读。

**面试追问地图：**

1. 幂等与去重有什么区别？
2. 为什么不能根据“正文相同 + 五秒内”判断同一次发送？
3. clientMessageId 冲突但正文不同应该怎样处理？
4. 幂等记录保存多久，过期后重放怎么办？
5. 为什么分布式锁不能替代唯一约束？

**事实等级：A。**

### 2.6 XSS 防护与上传安全

**业务问题：** 帖子、评论、搜索高亮和头像上传都接收不可信内容，可能导致存储型 XSS、路径穿越和恶意文件。

**项目做法：** 富文本用 Jsoup 白名单清洗，评论转安全纯文本；高亮先 HTML escape 再插入固定 em 标签；上传限制大小/MIME、实际图片解码，并使用 userId + UUID + 受控扩展名生成服务端路径。

**简历安全写法：**

> 对富文本、评论和搜索高亮实施服务端 XSS 防护，并对图片上传执行大小、MIME、实际解码和服务端随机文件名校验，避免仅信任前端过滤、Content-Type 或原始文件名。

**面试追问地图：**

1. 存储型、反射型、DOM 型 XSS 有什么区别？
2. HTML 白名单与输出编码分别适合什么内容？
3. Jsoup 之后为什么还需要 CSP 和 HttpOnly Cookie？
4. MIME、扩展名、魔数、实际解码为什么都不是单独充分条件？
5. 图片炸弹、SVG 脚本、恶意元数据和 CDN 缓存怎样处理？
6. 文件系统与数据库不在同一事务，孤儿文件怎样补偿？

**事实等级：A；对象存储和完整恶意文件扫描属于 C。**

### 2.7 Redis 缓存、降级、锁与一致性边界

**业务问题：** 首页聚合和通知未读数重复查询数据库；缓存重建时又可能出现并发回源。

**项目做法：** Redis 默认关闭；开启后 HomeCache/NotificationUnreadCache 保存可丢弃快照，异常回源 MySQL。首页 overview 使用短锁和 stale 值有限缓解击穿，解锁使用 token/Lua 思路；缓存不是事实源。

**简历安全写法：**

> 为首页统计与通知未读设计可选 Redis 缓存，以 MySQL 为事实源并支持异常回源；通过参数化 key、短 TTL、stale 值和带所有权 token 的锁缓解热点重建，同时明确当前未彻底消除缓存击穿。

不要写“使用 Redis 解决高并发”这种无法验证的空话。

**面试追问地图：**

1. 缓存穿透、击穿、雪崩分别是什么？
2. 空值缓存、Bloom Filter、互斥锁、逻辑过期分别解决什么？
3. TTL 为什么加随机值？Redis 整体宕机时数据库怎样自保？
4. Cache Aside 的读写步骤是什么？先更新库还是先删缓存？
5. 热 key、大 key 怎样发现和治理？
6. 分布式锁为什么要唯一 token + Lua 解锁？锁过期和续租怎么办？
7. Redis 的 RDB/AOF、主从、哨兵、Cluster 各解决什么，不解决什么？

**事实等级：B。真实 Redis 宕机、超时、序列化和并发压测尚未完成。**

### 2.8 RabbitMQ + Transactional Outbox + 消费幂等

**业务问题：** 业务事务提交成功后通知消息可能发送失败；消息确认窗口和消费者重试又会导致重复。

**项目做法：** Rabbit 默认关闭；可选路径在业务同库事务写 notification_outbox，发布器定时发送并处理 publisher confirm，配置主队列/DLQ，消费者用 event_key 幂等。

**简历安全写法：**

> 为通知链设计可选 RabbitMQ 异步方案，使用 Transactional Outbox 解决数据库提交与消息发送之间的可靠性窗口，结合 publisher confirm、重试、DLQ 与 event_key 消费幂等实现 at-least-once 下的业务去重。

不能写“实现 exactly-once”或“解决分布式事务”。

**面试追问地图：**

1. 数据库成功、MQ 失败怎么办？为什么本地事务无效？
2. publisher confirm、return、consumer ACK 分别证明什么？
3. ACK 前后宕机会怎样？为什么消息一定可能重复？
4. DLQ 由谁监控、怎样重放、怎样避免毒消息无限循环？
5. 消息积压怎样定位和扩容？为什么盲目加消费者可能压垮数据库？
6. 如何保证局部顺序？重试为何会破坏顺序？
7. Outbox 表怎样清理、分片和避免轮询热点？

**事实等级：B。真实 RabbitMQ confirm、网络中断和 DLQ 运维尚未集成验证。**

### 2.9 Elasticsearch 搜索副本、降级与 alias 重建

**业务问题：** MySQL LIKE 能提供基础搜索，但中文分词、相关性和规模有限；引入 ES 后又产生双写一致性和重建问题。

**项目做法：** 默认参数化 MySQL LIKE；ES 开启后优先检索，异常降级 MySQL。MySQL 是事实源，提交后按 id 同步；全量重建使用新索引并原子切换 alias。

**简历安全写法：**

> 设计 MySQL 基础搜索与可选 Elasticsearch 双层方案，将 ES 定位为可重建搜索副本；实现异常降级、提交后增量同步和版本化索引 + alias 原子切换的全量重建流程。

**面试追问地图：**

1. 为什么 ES 不适合作为本项目业务主库？
2. 倒排索引、分词器、相关性评分是什么？
3. MySQL 提交后 ES 失败怎样恢复？Outbox、CDC 各有什么取舍？
4. mapping 为什么难以原地修改？dynamic mapping 有何风险？
5. refresh、segment、merge 对实时性和性能有什么影响？
6. from/size 深分页为什么昂贵？search_after + PIT 怎样工作？
7. 分片越多越好吗？副本、可用性和容量怎样规划？

**事实等级：B。真实 ES、中文插件、故障降级和大数据重建未集成验证。**

### 2.10 持久化私信 + 游标分页 + SSE 实时体验

**业务问题：** 消息不能因应用重启丢失，重试不能重复，猜测 conversationId 不能越权，实时连接断开后必须恢复。

**项目做法：** MySQL 保存 conversation/member/private_message；排序 pair_key 保证单聊唯一，clientMessageId 保证发送幂等，beforeId 做游标分页，成员表维护未读；事务提交后才通过 SseEmitter 推送。

**简历安全写法：**

> 实现 MySQL 持久化单聊，使用排序 pair_key、clientMessageId、成员权限校验和 beforeId 游标分别处理会话唯一性、重试幂等、水平越权与稳定分页；SSE 仅作为提交后的实时通知层，断线通过历史补拉恢复。

**面试追问地图：**

1. 为什么实时通道不能替代持久化？
2. SSE、WebSocket、长轮询各适合什么场景？
3. 已发送、已送达、已读怎样定义？
4. 原生 EventSource 怎样携带认证？JWT 放 URL 有什么风险？
5. 多实例怎样找到持有用户连接的节点？
6. 心跳、重连风暴、慢客户端、背压和有界队列怎样处理？
7. 游标分页怎样选择稳定排序与复合索引？

**事实等级：A（数据库主链）；B（浏览器 SSE，多实例和代理环境尚未端到端验证）。**

### 2.11 管理状态机、乐观并发与事务审计

**业务问题：** 管理员操作影响用户权利，必须防越权、防非法状态转换、防并发覆盖并可追责。

**项目做法：** 拦截器认证 + Service ADMIN 授权 + 资源规则三层检查；状态机限制转换；旧状态条件 UPDATE 检测竞争；处罚、状态和审计同事务；禁言到期同时有定时扫描和请求时惰性解除。

**简历安全写法：**

> 为后台治理实现认证、管理员授权、资源限制三层校验，以显式状态机和旧状态条件更新阻止非法转换与并发覆盖，并将处罚、状态变更和审计日志纳入同一事务。

**面试追问地图：**

1. 认证、授权、资源所有权有什么区别？
2. RBAC、ACL、ABAC 分别适合什么权限需求？
3. 为什么隐藏管理按钮不是安全措施？
4. 审计为什么要与状态同事务？跨系统审计怎么办？
5. 审计表怎样防篡改，WORM/哈希链又有什么边界？
6. 多实例定时任务怎样避免重复？幂等与调度锁分别做什么？
7. 高风险操作为什么需要 MFA、再认证或双人审批？

**事实等级：A；MFA、防篡改远程审计和完整先审后发流程属于 C。**

## 5. 面试时的统一回答框架

遇到任何技术题，都按下面七句话组织：

1. **业务问题：** 当时要防止或优化什么？
2. **最小方案：** 如果不用复杂中间件，第一版怎样保证正确？
3. **项目实现：** 哪个 Controller/Service/Mapper/表真正完成？
4. **技术作用：** 该技术只解决链路中的哪一段？
5. **替代方案：** 为什么当前没选另一个同类技术？
6. **代价与缺陷：** 新增了什么一致性、性能或运维问题？
7. **演进条件：** 数据量或需求达到什么程度才升级？

示例：

> 首页统计每次做多条聚合 SQL，重复查询会浪费数据库资源，所以提供可选 Redis 快照缓存；MySQL 仍是真相，缓存异常回源。overview 用短锁和 stale 值缓解热点 key 过期，但首次加载和 hotTags 仍可能击穿，因此我不会说已经彻底解决。若压测显示数据库在缓存故障时无法承受峰值，再补 TTL 抖动、限流熔断、多级缓存和真实故障演练。

这个回答既能展示 Redis，也主动给面试官留下穿透、击穿、雪崩、一致性、分布式锁和降级等追问入口。

## 6. 学习顺序

1. 先吃透 A 级：MySQL 不变量、事务、JWT 鉴权、幂等和权限。
2. 再学习 B 级：Redis、RabbitMQ、Elasticsearch、SSE；每项先说边界，再说常见故障。
3. 最后准备 C 级演进：refresh token、对象存储、混合 Feed、MFA、审计防篡改。
4. 每学完一项，用对应 `DesignFromZeroFXX.md` 的折叠自测题闭卷回答。

真正值得写在简历上的不是“我用过多少中间件”，而是你能说明它为什么出现、解决了哪一步、没解决什么，以及故障后系统怎样恢复。
