# 紫荆论坛复现路线图

## 为什么按功能分包

一个功能的接口、业务规则、数据模型和基础设施放在同一根包下，更容易在 IDEA 中按“一个功能一次闭环”的方式学习。公共代码只放真正跨功能的能力，例如统一响应、异常、认证上下文和时间抽象。

## 建议提交节奏

每个功能至少拆成四次可运行提交：

1. `design`：API、DTO、VO、DDL 和测试用例先落地。
2. `entity-mapper`：Entity、Mapper 和数据库集成测试。
3. `service`：Service/ServiceImpl、事务、权限和业务规则。
4. `controller`：Controller、鉴权、异常映射和 MockMvc 测试。

Redis、RabbitMQ、Elasticsearch、WebSocket 等进阶能力单独提交，不与第一版正确性混在一起。

## 里程碑

| 里程碑 | 功能 | 完成证明 |
| --- | --- | --- |
| M0 | 工程基线 | `mvn test` 通过，两个基线接口可访问 |
| M1 | F01-F02 | 两账号验证登录和资源所有权 |
| M2 | F03-F04 | 发帖、详情、评论、回复、删除闭环 |
| M3 | F05-F06 | 重复/并发请求幂等，关系和计数可对账 |
| M4 | F09 | Redis 停机可降级，缓存删除可重建 |
| M5 | F07-F08 | MQ 重投不重复，ES 索引可重建 |
| M6 | F11-F10 | 管理审计完整，私信重启不丢且不可越权 |

## 每包完成定义

- 正常、边界、异常、越权、重复请求、并发请求均有可执行测试。
- DDL 明确主键、唯一约束、索引、外键取舍和时间字段。
- 写操作的事务边界明确；外部副作用在事务提交后处理。
- 能从浏览器请求追到 Controller、ServiceImpl、Mapper 和数据表。
- 能停止一个外部依赖并说清现象、数据风险、降级和恢复步骤。

## 参考源码阅读规则

先写自己的产品规则和接口，再按对应 `GUIDE.md` 中的“参考入口”读取参考项目。只对照命名、边界和缺陷，不整文件复制；参考项目中存在的安全、正确性或一致性问题也要记录下来。
